# GB10-Engine
[English](README.md) · [简体中文](README.zh-CN.md) · [日本語](README.ja.md) · [한국어](README.ko.md) · [Español](README.es.md) · [Français](README.fr.md) · [Deutsch](README.de.md) · **Русский** · [Português](README.pt-BR.md)

Написанный с нуля движок вывода на чистом Rust для **Qwen3.8-27B (NVFP4)** на
**NVIDIA DGX Spark GB10** (`sm_121`, CUDA 13), проверенный в прямом сравнении с
**llama.cpp** на тех же весах, той же машине и том же стенде.

- Собственные ядра CUDA, скомпилированные в PTX для `sm_121`, без стороннего runtime вывода.
- Гибрид Gated DeltaNet + полное внимание, 64 слоя, нативный контекст **262,144** token.
- HTTP-эндпоинты, совместимые с OpenAI **и** Anthropic, стриминг, непрерывная батчинг.
- Каждое число в этом README воспроизводится скриптом из данного репозитория.

## Бенчмарк: GB10-Engine против llama.cpp

**Это тот раздел, который стоит прочитать.** Та же машина, тот же чекпоинт NVFP4 (gb10-engine читает
чекпоинт `modelopt` NVFP4; llama.cpp читает GGUF, сконвертированный из тех же весов), те же промпты,
тот же клиент, запуски строго последовательные, так что GPU не достаётся единолично ни одному из соперников.

### Конфигурация теста

| | |
|---|---|
| Оборудование | NVIDIA DGX Spark **GB10**, `sm_121`, 48 SMs, 121.7 GiB unified LPDDR5X |
| Измеренная пропускная способность чтения | **228 GB/s** (см. [`docs/PHYSICS.md`](docs/PHYSICS.md)) |
| gb10-engine | `./target/release/gb10-server --model models/Qwen3.8-27B-NVFP4 --ctx 262144` |
| llama.cpp | `llama-server -m models/Qwen3.8-27B-NVFP4.gguf -c 262144 -ngl 99 -fa on` |
| Клиент | [`bench/longctx/ttft.py`](bench/longctx/ttft.py) — идентичный запрос дважды за пробу, уникальный ведущий маркер, чтобы «тёплое» попадание не могло оказаться ложным |
| Декодирование | жадное, `max_tokens 128` |
| Префиксный кэш | включён у обоих (именно это делает **warm TTFT** осмысленным) |

**Определения метрик**, потому что «TTFT» скрывает реальный вопрос:

- **Cold TTFT** — префикс никогда не встречался, поэтому весь промпт префиллится заново. Это
  измерение вычислительной стоимости префилла.
- **Warm TTFT** — тот же самый запрос ещё раз, так что префиксный кэш может пропустить префилл. Это
  измерение попадания в кэш.
- **OTPS** — выходные token в секунду во время декодирования.

> **Сравнимы только пары из одной сессии.** Идентичный код показал разницу **23%** на этой машине в
> разные дни (см. «Замечания о методологии»). Каждое соотношение ниже получено из пары, измеренной в
> одной сессии; в каждой ячейке не менее двух независимых измерений.

### Пропускная способность декодирования (OTPS) — gb10-engine побеждает в 3 из 4

| Контекст | gb10-engine | llama.cpp | Результат |
|---|---|---|---|
| 8K | **8.91** | 7.26 | **1.23x быстрее** |
| 32K | **7.14** | 6.865 | **1.04x быстрее** |
| 128K | **5.29** | 4.75 | **1.11x быстрее** |
| 256K | 3.665 | **3.86** | 1.05x медленнее |

### TTFT — gb10-engine побеждает в каждой warm-ячейке и отстаёт в каждой cold-ячейке

| Контекст | Cold TTFT (gb10 / llama.cpp) | Warm TTFT (gb10 / llama.cpp) |
|---|---|---|
| **8K** | 10.35 s / **9.50 s** — 1.09x медленнее | **0.03 s** / 0.223 s — **7.4x быстрее** |
| **32K** | 80.00 s / **44.55 s** — 1.80x медленнее | **0.05 s** / 0.29 s — **5.8x быстрее** |
| **128K** | 890.54 s / **275.04 s** — 3.24x медленнее | **0.14 s** / 0.48 s — **3.4x быстрее** |
| **256K** | 3295.45 s / **726.22 s** — 4.54x медленнее | **0.28 s** / 0.66 s — **2.36x быстрее** |

**Читайте эту таблицу честно: это раздельное решение.**

- **Warm TTFT: выиграно 4 из 4**, с преимуществом от 2.4x до 7.8x. Как только префикс закэширован, этот движок
  возобновляет работу за 0.03–0.28 s там, где llama.cpp нужно 0.22–0.66 s. Для агентных, RAG- и многоходовых
  нагрузок, которые повторно отправляют длинный префикс, именно эта метрика определяет время на настенных часах.
- **OTPS: выиграно 3 из 4**, с преимуществом от 1.04x до 1.23x. В ячейке 256K отставание 1.05x.
- **Cold TTFT: выиграно 0 из 4.** Этот движок отстаёт на 1.09x при 8K и на 4.54x при 256K. **Это
  открытая проблема**, и это арифметика: 16 слоёв полного внимания выполняют квадратичную работу префилла,
  а ядро внимания префилла работает на ~8% от пика fp16 CUDA-core данной части.

**Прогресс по cold TTFT, достигнутый в текущем раунде работы** (измерено на сервере, под контролем
проверки корректности `chunked-prefill`):

| Контекст | Cold TTFT до | Cold TTFT сейчас | Улучшение |
|---|---|---|---|
| 8K | 14.93 s | **10.35 s** | **1.43x** |
| 32K | 90.54 s | **80.00 s** | **1.13x** |
| 128K | 1134.63 s | **890.54 s** | **1.28x** |
| 256K | 4138.39 s | **3295.45 s** | **1.25x** |

### Точность — gb10-engine точнее llama.cpp на тех же весах

**Perplexity** (WikiText-2, `n_ctx 512`, 580 окон, 147,900 предсказаний — та же конфигурация,
что и в историческом baseline):

| Реализация | Веса | Perplexity | против BF16 |
|---|---|---|---|
| **gb10-engine** | **NVFP4** | **7.1006** | +0.71% |
| llama.cpp | NVFP4 (тот же GGUF) | 7.2088 | +2.24% |
| transformers (эталон) | BF16 (базовая модель) | **7.0506** | — |

**MMLU** (3,240 вопросов, согласие по 4 вариантам):

| Реализация | Веса | MMLU | Верно |
|---|---|---|---|
| transformers (эталон) | BF16 | **80.74%** | 2616/3240 |
| **gb10-engine** | **NVFP4** | **80.34%** | **2603/3240** |
| torch, NVFP4 деквантованный | NVFP4 | 80.46% | 2607/3240 |
| llama.cpp | NVFP4 (тот же GGUF) | 79.88% | 2588/3240 |

**Почему эти числа говорят, что путь квантования корректен:**

- gb10-engine **на 1.5% лучше llama.cpp** по perplexity и **на +0.46 п.п. лучше по MMLU**, используя
  *те же* веса NVFP4. Движок не теряет точность относительно зрелой реализации.
- Он находится **на 0.71% выше BF16** по perplexity и **на 0.40 п.п. ниже BF16** по MMLU — ожидаемая цена
  4-битных весов для вывода без активаций/градиентов, и то же направление и величина, что и у
  независимого эталона с деквантованным torch.
- Стенд **сверяет tokenizer с `llama-tokenize` и сообщает 0 несовпадений на
  297,054 token**, так что ни одно различие в точности здесь не является артефактом токенизации.
- Корректность также проверяется по раундам: точное совпадение token с замороженными трассами-оракулами HuggingFace
  (64 слоя, жадное декодирование), плюс проверка паритета батчей.

### Известная проблема: извлечение на длинном контексте сейчас не сертифицировано

Валидация «иголка в стоге сена» ([`bench/longctx/run_validation.sh`](bench/longctx/run_validation.sh))
зафиксировала **3/3 при 32K, 1/1 при 128K, 1/1 при 256K**. **Повторный запуск идентичного плеча 32K теперь даёт
0/3 на gb10-engine *и* 0/3 на llama.cpp**, поэтому сбой был прослежен и движок не был к нему причастен:

- сбои детерминированы (`finish_reason: stop`, `completion_tokens: 0` — EOS в качестве первого token);
- они нерегулярны по *длине*, а не монотонны, что не похоже на регрессию точности KV;
- они **идентичны при `temperature: 0`**, с `--no-prefix-cache`, с `PREFILL_CHUNK` 2048
  *и* 8192, а также при `enable_thinking` опущенном/ложном/истинном;
- **и llama.cpp сбоит на тех же промптах.**

**Вывод: точность на стандартных метриках нормальна; извлечение на длинном контексте сегодня этим стендом
ни сертифицировано, ни опровергнуто.** Это отслеживается открыто, а не опускается. Полное описание в
[`bench/longctx/comparison.md`](bench/longctx/comparison.md).

### Воспроизведите сами

```bash

./target/release/gb10-verify perplexity --model models/Qwen3.8-27B-NVFP4 \
    --tokens bench/ppl/wiki.tokens.txt --text bench/ppl/wiki.test.raw --ctx 512 --chunks 580

# correctness + benchmark gate (build, tests, token-exact oracle, batch parity, attn tiling, bench)

```

**Не запускайте измерение через сервер и гейт одновременно** — гейт запускает и останавливает
серверы на порту 8080 и убьёт сервер посреди запроса.

### Где производительность находится относительно roofline оборудования

> **Сначала прочитайте [`docs/PHYSICS.md`](docs/PHYSICS.md).** В исходном запросе требовалось 100 tok/s
> для одного потока. Измерено на этой машине: GB10 устойчиво обеспечивает **228 GB/s** пропускной способности
> чтения, и этот чекпоинт требует **17.608 GB** трафика весов на token, поэтому roofline одного потока
> составляет **12.95 tok/s**, а нижняя граница на шаг — **77.2 ms**. Цель в 100 tok/s требует ~1.76 TB/s —
> **7.7x от измеренной пропускной способности** — так что ни одна реализация не может её достичь.
> Согласованный контракт в [`docs/TARGETS.md`](docs/TARGETS.md) отражает то, что оборудование действительно может.

Оставшийся разрыв в cold-префилле — это одно ядро: тайловое внимание префилла работает на **3.12 TFLOP/s,
~8.4% от пика fp16 CUDA-core**, и его поток инструкций лишь на 42.4% состоит из арифметики, поэтому оно
ограничено выдачей инструкций. Закрытие разрыва cold TTFT на длинном контексте требует переписывания этого ядра
с использованием `mma.sync` tensor core; план и требуемые ускорения (1.29x при 8K, 5.98x при 32K, 8.40x при 128K,
8.82x при 256K) находятся в [`bench/longctx/comparison.md`](bench/longctx/comparison.md).

## Быстрый старт

```bash
# correctness foundation (no GPU needed)
cargo test -p gb10-core

# hardware physics, if you want to re-derive the roofline yourself
nvcc -arch=sm_121 -O3 -o bench/hw/bw bench/hw/bw.cu && ./bench/hw/bw
python3 scripts/weight_traffic.py

# build everything and serve
cargo build --release
./target/release/gb10-server --model models/Qwen3.8-27B-NVFP4
```

Загрузка весов занимает около **40 s**, после чего сервер обслуживает запросы на `127.0.0.1:8080`.

## Модель

`nv-community/Qwen3.8-27B-NVFP4`, загружается через ModelScope CLI:

```bash
modelscope download --model nv-community/Qwen3.8-27B-NVFP4 \
    --local_dir models/Qwen3.8-27B-NVFP4
```

`models/` — это символическая ссылка на каталог загруженного чекпоинта, и она не отслеживается git.

Архитектура: `qwen3_5`, 64 слоя (48 слоёв линейного внимания Gated-DeltaNet + 16 слоёв полного внимания каждый
4-й слой), hidden 5120, 24 головы запросов / 4 головы KV (группа GQA 6), head_dim 256, частичное RoPE (0.25,
mRoPE interleaved), vocab 248320, **1 слой MTP**, нативные **262,144** позиции. Квантование —
modelopt MIXED_PRECISION: NVFP4 (группа 16) для всех MLP и `lm_head`, FP8 для каждой проекции
внимания, а веса MTP/vision оставлены неквантованными. Размер на диске 21.921 GB.

## Использование локального эндпоинта

Сервер говорит и на проводном протоколе OpenAI, и на протоколе Anthropic на `127.0.0.1:8080`.

| route | протокол | примечания |
|---|---|---|
| `POST /v1/chat/completions` | OpenAI | поддерживает `stream`, `max_tokens`, `enable_thinking` |
| `POST /v1/completions` | OpenAI | устаревшее текстовое дополнение; `prompt` должен быть одной строкой |
| `POST /v1/messages` | Anthropic | поддерживает `stream`, `max_tokens` |
| `GET /v1/models` | оба | возвращает id загруженной модели |
| `GET /health` | — | проверка живости; используйте это, чтобы дождаться запуска |

```sh
curl http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"m","messages":[{"role":"user","content":"Count from one to five."}],"max_tokens":16}'
```

### Длина контекста и параллелизм

Окно контекста задаётся `--ctx` (**по умолчанию 32768**) вплоть до **262144** позиций чекпоинта, а
`--concurrency` задаёт, на сколько последовательностей рассчитан KV-кэш. По умолчанию параллелизм таков, какой
покрывает бюджет KV в 40 GB, с потолком 16, так что длинный контекст автоматически его снижает:

```sh
./target/release/gb10-server --model models/Qwen3.8-27B-NVFP4 --ctx 262144
# context 262144 tokens, 1 concurrent sequence(s), KV cache 34.4 GB
```

> **Для любого бенчмарка с длинным контекстом `--ctx` обязателен.** Без него сервер работает на 32768, и
> более длинный промпт возвращает **вообще никакого содержимого**, а не ошибку — молчаливый сбой, который
> выглядит как баг клиента.

**Параллелизм.** Сервер объединяет до 16 одновременных запросов в один прямой проход,
собирая их в течение окна в 25 ms. Установите `GB10_BATCH_LOG=1`, чтобы логировать размер группы на каждом
шаге — 16 параллельных запросов должны залогировать `batch of 16`. При идентичных промптах все 16 возвращают
байт-идентичные ответы.

**Ответы очищаются от блока рассуждений модели.** `enable_thinking` по умолчанию `true`
(в соответствии с чекпоинтом), поэтому шаблон помещает открывающий ` thinking` в промпт, а генерация
возвращает рассуждения, за которыми следует `</think>`; эндпоинт удаляет всё вплоть до этого тега, так что
`content` — это сам ответ. **Передайте `"enable_thinking": false` для более короткого, прямого ответа без
каких-либо сгенерированных рассуждений.** **Стриминг всё ещё пропускает рассуждения через себя** — см.
[`docs/NEXT.md`](docs/NEXT.md), где описано запланированное исправление и ловушка с усечением, которую ему
нужно обойти.

Аутентификация не реализована, и слушатель привязан к loopback; добавьте прокси перед ним, если
он должен быть доступен откуда-то извне.

## Цикл

`loop/run_round.sh` — драйвер итераций. Каждый раунд:

1. `cargo build --release --workspace`
2. `cargo test --workspace --release`
3. гейт корректности: точное совпадение token с замороженными трассами-оракулами HF
4. гейт бенчмарка: свежий артефакт, записанный в `bench/results/`
5. коммит и push в `omnigeeker/GB10-Engine`

Долговременное состояние хранится в `loop/state.json`; отчёты по раундам — в `loop/rounds/`. Раунд, не
прошедший гейт, записывается как `FAIL` и не продвигает этап.

## Замечания о методологии

Три правила, которые этот проект выучил на собственном горьком опыте и применяет к каждому числу выше:

1. **Сравнимы только пары из одной сессии.** Идентичный код на fp32 показал 90.54 s и 111.59 s
   (+23.2%) в разные дни на этой машине; число llama.cpp для 32K дрейфовало с 44.55 s → 53.60 s за
   тот же период. Соотношения сохранились, абсолютные секунды — нет.
2. **Измеренный эффект — это не атрибутированная причина.** Пропускная способность декодирования на 128K и 256K
   улучшилась ~на 23% за время этой работы, тогда как 8K/32K в точности воспроизвели свои записанные значения.
   То, что улучшение реально, — измерено; *почему* — всё ещё не атрибутировано, и это записано именно так.
3. **Проба измеряет чувствительность, а не запас.** Проба занятости, показывающая, что ядро стоит в 1.47x
   больше при половине занятости, ничего не говорит о том, можно ли занятость поднять — для этого нужна
   арифметика ресурсов (здесь: 2 блока/SM сегодня, для 3 потребовалось бы сокращение shared memory на 22%).
